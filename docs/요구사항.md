# 기능 요구사항

연구 주제 추천 서비스의 범위를 고정하기 위한 문서입니다. 여기 없는 기능은 만들지 않습니다. 새 기능이 떠오르면 바로 구현하지 말고 [12장 백로그](#12-백로그)에 먼저 적습니다.

- **작성일:** 2026-11-05
- **관련 문서:** [topic_recommendation_workflow.md](topic_recommendation_workflow.md) (다섯 상태의 세부 흐름), [설계서.md](설계서.md) 10장 (판단 기준 J-1~J-8)
- **상태:** 아래 표의 요구사항은 모두 확정입니다. 확정이 아닌 항목만 따로 **보류**라고 표시합니다.
- **우선순위:** **P0** 없으면 서비스가 아님 / **P1** 시연 전에 필요 / **P2** 여유가 있으면

## 1. 목표

사용자가 자기 연구실과 관심사에 맞고 기존 연구와 겹치지 않는 **새로운 연구 주제 후보**를 받는다.

이 목표에 직접 기여하지 않는 기능은 P2 이하로 둡니다.

## 3. 세션과 대화 기록

| ID | 요구사항 | 우선 |
|---|---|---|
| S-1 | 세션은 사용자별로 관리된다. 다른 사용자의 세션은 보이지 않는다. | P0 |
| S-2 | 각 세션은 대화 메시지 목록으로 저장된다. | P0 |
| S-3 | 비로그인 사용자의 세션과 대화 목록은 브라우저 세션 스토리지에 저장된다. | P0 |
| S-4 | 사이드바에서 세션 목록을 보고, 새 세션을 만들고, 이전 세션을 열 수 있다. | P0 |
| S-5 | 세션을 다시 열면 대화뿐 아니라 **현재 상태(①~⑤)와 상태별 선택 결과**(고른 문제, 세부 흐름, 후보, 판정)도 복원된다. | P0 |
| S-6 | 세션 제목은 첫 질의나 선택한 문제로 자동 생성되고, 사용자가 바꿀 수 있다. | P1 |

| P-3 | 로그인 사용자의 프로필은 계정에 저장되어 새 세션에서 다시 입력하지 않는다. | P1 |
| P-4 | 세션은 시작 시점의 프로필을 복사해 둔다. 프로필을 나중에 고쳐도 기존 세션의 추천 근거는 바뀌지 않는다. | P1 |

## 5. 채팅과 추천

| ID | 요구사항 | 우선 |
|---|---|---|
| C-1 | 사용자는 채팅창으로 LLM에게 질의할 수 있다. | P0 |
| C-2 | 사용자는 새로운 연구 주제 후보를 받을 수 있다. | P0 |
| C-3 | LLM 응답은 스트리밍으로 표시된다. | P1 |
| C-4 | 추천 문제, 세부 흐름, 후보 주제에는 **출처 논문과 원문 인용**이 붙는다. 출처 없는 주장은 표시하지 않는다 (설계서 J-1, J-8). | P0 |
| C-5 | 추천과 후보는 채팅 텍스트가 아니라 **선택 가능한 카드**로 보여 주고, 카드를 눌러 다음 상태로 넘어간다. 채팅으로도 선택할 수 있다. | P0 |
| C-6 | 사용자는 추천을 거절하고 이유를 남길 수 있다. 거절 이유는 다음 추천에 반영된다. | P1 |
| C-7 | 자기 아이디어를 직접 입력하면 ③ 주제 다듬기로 바로 간다 (워크플로우 1.4). | P2 |

## 6. 진행 상태 표시

| ID | 요구사항 | 우선 |
|---|---|---|
| F-1 | 사용자는 다섯 상태(둘러보기, 문제 파고들기, 주제 다듬기, 검증, 확정)를 UI로 확인할 수 있다. | P0 |
| F-2 | 현재 상태가 강조되고, 지나온 상태에는 그때 고른 것이 요약된다. | P0 |
| F-3 | 지나온 상태를 눌러 그 상태로 돌아갈 수 있다. 돌아가도 이미 수집한 결과는 재사용한다 (워크플로우 "되돌아가는 경로"). | P1 |
| F-4 | 오래 걸리는 단계(검색, 검증)는 진행 중인 하위 단계를 보여 준다. 예: "관련 논문 검색 중 (23/60)". | P0 |
| F-5 | ④ 검증 중에는 채팅 입력과 카드 선택을 잠근다. 검증이 끝나야 다시 입력할 수 있다. 백그라운드 검증은 하지 않는다. | P0 |
| F-6 | 외부 API가 실패하면 실패한 단계와 재시도 버튼을 보여 준다. 대화는 날아가지 않는다. | P0 |

### 6.1 생성 중 다른 세션으로 이동

사용자는 응답이나 검증이 진행되는 도중에 다른 세션을 열 수 있습니다. 이때 결과가 엉뚱한 세션에 섞이거나 사라지면 안 됩니다.

| ID | 요구사항 | 우선 |
|---|---|---|
| G-1 | 모든 생성 작업은 **시작한 세션의 ID**에 묶인다. 결과는 그 세션에만 저장되고, 지금 화면에 열린 세션에는 절대 쓰지 않는다. | P0 |
| G-2 | 한 세션에서는 생성 작업이 한 번에 하나만 돈다. 진행 중에는 그 세션의 입력을 잠근다 (F-5와 같은 방식). | P0 |
| G-3 | 생성 도중 다른 세션으로 이동하면 진행 중인 작업을 **취소**한다. 백그라운드로 계속 돌리지 않는다 (F-5와 같은 이유). | P0 |
| G-4 | 취소된 작업은 원래 세션에 "중단됨" 메시지로 남는다. 스트리밍으로 받은 부분 응답이 있으면 함께 남기고, 중단되었다고 표시한다. | P0 |
| G-5 | 원래 세션으로 돌아오면 "중단됨" 메시지 옆에 재시도 버튼이 있다. 재시도할 때 이미 받아 둔 검색·검증 결과는 재사용한다. | P1 |
| G-6 | 취소된 작업은 상태(①~⑤)를 바꾸지 않는다. 상태는 작업이 끝까지 성공했을 때만 넘어간다. | P0 |
| G-7 | 생성 중에 세션을 삭제하거나 로그아웃해도 G-3과 같이 작업을 취소하고, 남은 결과는 버린다. | P1 |

## 11. 결정이 필요한 것

1. ~~세션 스토리지와 로컬 스토리지~~ → **결정 (2026-11-05): 세션 스토리지.** 비로그인 사용자의 대화와 결과는 탭을 닫으면 사라집니다. 세션 스토리지는 탭마다 따로라서, 비로그인 사용자는 탭끼리 세션을 공유하지 않습니다.
2. ~~Streamlit에서 브라우저 저장소 쓰기~~ → **결정 (2026-11-05): Streamlit을 버리고 FastAPI + HTML/JS로 전환.** Streamlit은 브라우저 저장소에 직접 접근하지 못하고, 클릭할 때마다 스크립트를 다시 실행해서 생성 중 세션 이동(6.1)을 통제하기 어렵습니다. `src/`에는 Streamlit 코드가 없어 화면(`app.py`)만 다시 만들면 됩니다. API는 [API_명세.md](API_명세.md)에 있습니다.
3. ~~인증 방식~~ → **결정 (2026-11-05): Google 로그인, Supabase Auth로 처리.** 비밀번호를 직접 저장하지 않아 해시·재설정 같은 일이 없습니다. FastAPI에서는 Authlib으로 붙이고, Google Cloud에서 OAuth 클라이언트를 한 번 만들어야 합니다. 이메일+비밀번호는 가입·비밀번호 재설정 화면까지 직접 만들어야 해서 범위가 커집니다.
4. ~~로그인 사용자 데이터 저장소~~ → **결정 (2026-11-05): 먼저 로컬 폴더(`DB/`)로 구현하고, Supabase(무료 플랜)로 옮김.** Render 디스크가 재시작 때 지워지기 때문입니다. 구조는 [설계서.md](설계서.md) 6장.

# 설계서

[요구사항.md](요구사항.md)와 [API_명세.md](API_명세.md)를 어떻게 구현할지 정합니다. 특히 외부 서비스(Solar, Upstage Studio, S2)가 각 단계에서 무엇을 맡는지, 그리고 ④ 검증을 어떻게 하는지를 다룹니다.

- **작성일:** 2026-11-05
- **마감:** 2026-11-06 자정
- **완료 기준:** `mock/persona/persona.json` 사용자로 ①~⑤가 끊김 없이 돈다. 시간이 남으면 다른 프로필로도 확인한다.
- **가져온 형식:**
  - 연구 카드: `evaluation_v2/reconstruction_plan.md` 조건 C의 논문 카드 (`recon/runs/cards_t00X.json`)
  - 후보 형식과 비평 기준: `evaluation_v2-branches/loop2`의 ScholarIdeas 7요건과 `review.md`, `overlap.md` 프롬프트

## 1. 역할 분담

원칙은 **Studio는 읽고, Solar는 비교하고, 코드가 판정한다**입니다. LLM에게 "중복이냐"를 직접 묻지 않습니다. 판정은 같은 입력이면 같은 결과가 나오는 코드가 내립니다.

| 담당 | 하는 일 | 쓰는 곳 |
|---|---|---|
| **Studio 에이전트 A** (있음) | 서베이 PDF → unit Open Problems 추출 | 오프라인 DB 구축 |
| **Studio 에이전트 B** (새로 만듦) | 논문 PDF → **연구 카드** (본문 기준, 원문 인용 포함) | ④ 검증 |
| **Solar chat** | 검색어 작성, 추천 이유, 후보 생성, 요소별 비교, 비평, 대화 | ①~⑤ |
| **Solar embedding** | 프로필·후보 임베딩, 유사도로 논문 줄이기 | ①, ④ |
| **S2** | 논문 검색, 초록·오픈액세스 PDF 주소 | ③, ④ |
| **코드** | 인용 검증(`textnorm.contains`), 점수 합산, 판정, 예산, 캐시 | 전 단계 |
| **Supabase** | Google 로그인(Auth), 사용자 데이터·작업 결과·캐시 저장(Postgres) | 로그인, 저장 (6.3) |

## 2. 전체 구조

```text
static/index.html, app.js ── 화면, sessionStorage, 입력 잠금, SSE 수신
        │
server.py (FastAPI) ─────── 라우팅, 인증, 작업 잠금, 예산, 호출 로그
        │
src/
  recommend.py   ①  (있음, 수정)
  chat.py        대화 (있음, 수정)
  research.py    ③  (있음, 수정) ─ references.py, multi_agent.py
  verify.py      ④  (새로 작성)
  finalize.py    ⑤  (새로 작성, 코드만)
  studio.py      Studio 에이전트 호출 (새로 작성)
  store.py       저장 계층. 지금은 DB/ 폴더, 이후 Supabase (새로 작성)
  calllog.py     호출 로그 (새로 작성)
```

## 3. 상태별 처리

| 상태 | API | 처리 | 담당 | 지금 코드 |
|---|---|---|---|---|
| ① 둘러보기 | `/api/recommend` | 프로필 → 검색어 → 임베딩 검색 → 선별 → 추천 이유 | Solar, 코드 | `recommend()` |
| ② 문제 파고들기 | `/api/chat` | 고른 문제를 두고 대화로 조건 추가 | Solar | `reply_stream()` |
| ③ 주제 다듬기 | `/api/research` | 검색어 → S2 → 후보 제안·상호 검토·토너먼트 → 후보 3개 | Solar, S2 | `generate_research()` |
| ④ 검증 | `/api/verify` | [4장](#4-검증-상세) | Studio, Solar, S2, 코드 | 없음 |
| ⑤ 확정 | `/api/finalize` | 저장된 값으로 최종 주제 카드 조립 | 코드 | 없음 |

②와 ③ 사이에서는 지금처럼 사용자가 "후보 생성" 버튼을 누릅니다. ③에서 후보를 하나 고르고 대화로 다듬은 뒤 "검증" 버튼을 누르면 ④로 넘어갑니다.

## 4. 검증 상세

### 4.1 흐름

```text
입력: ③에서 고른 후보 (title, gap, approach, evaluation)
 │
 ├─ V1 [Solar]   후보로 검증 검색어 3개 작성
 ├─ V2 [S2]      검색. ③에서 받은 참고문헌과 합치고 중복 제거
 ├─ V3 [임베딩]  후보와 유사도 상위 15편으로 줄임            ← 비용 필터일 뿐 판정에 쓰지 않음
 ├─ V4 [Solar]   15편 각각의 초록으로 연구 카드 작성 (초록 수준)
 ├─ V5 [Solar]   후보와 카드를 요소별로 비교 → [코드] 점수 합산 → 최근접 3편
 │
 ├─ V6 [Studio B] 최근접 3편의 PDF → 본문 연구 카드 (동시에 3개 job)
 │      ├ PDF 순서: openAccessPdf → S2 arXiv ID → arXiv 제목 검색 (제목이 같을 때만). 출판사 차단은 우회하지 않음
 │      └ PDF가 없거나 실패 → 그 논문은 V4의 초록 카드 유지, "초록 수준"과 못 읽은 이유 표시
 ├─ V7 [Solar]   본문 카드로 요소별 다시 비교
 ├─ V8 [코드]    판정 (4.4)
 └─ V9 [Solar]   비평: ScholarIdeas 7요건 + 검토 필드 (4.5)
 │
출력: 판정, 최근접 논문 3편과 요소별 근거, 비평
```

`progress` 이벤트의 `step`은 `queries` · `search` · `narrow` · `abstract_cards` · `nearest` · `fulltext` · `compare` · `critique`입니다. V6에서는 `"본문 분석 중 (2/3)"`처럼 논문 단위로 보냅니다 (F-4).

### 4.2 연구 카드

evaluation_v2의 논문 카드 형식에 **필드별 원문 인용**과 **읽은 수준**을 더했습니다. 초록 카드(V4)와 본문 카드(V6)가 같은 형식입니다.

```json
{
  "paper_id": "S2 paperId",
  "title": "...",
  "level": "abstract | fulltext",
  "problem":     { "text": "무엇을 풀려는가",       "quote": "원문 그대로", "page": 2 },
  "method":      { "text": "어떻게 푸는가",          "quote": "...", "page": 4 },
  "assumptions": { "text": "무엇을 전제하는가",      "quote": "...", "page": 3 },
  "evaluation":  { "text": "무엇과 비교해 무엇으로 재는가", "quote": "...", "page": 7 },
  "limitations": { "text": "스스로 밝힌 한계",       "quote": "...", "page": 9 }
}
```

| 규칙 | 이유 |
|---|---|
| 원문에 없으면 `text`, `quote`를 빈 문자열로 둔다. 지어내지 않는다 | evaluation_v2 카드 규칙 그대로 |
| `quote`는 코드가 원문과 대조한다. 초록 카드는 초록과, 본문 카드는 Studio 파싱 결과와 대조한다. 통과하지 못하면 그 필드는 빈 것으로 본다 | [J-1](#j-1-인용-대조) |
| 초록 카드는 `page`가 `null` | |
| `limitations`는 점수에 넣지 않는다. ⑤의 "빈틈" 근거로만 쓴다 | 한계는 겹침이 아니라 후보가 파고들 자리 |

### 4.3 요소별 비교 (V5, V7)

후보와 카드를 네 요소로 맞춰 비교합니다.

| 요소 | 후보 쪽 | 카드 쪽 |
|---|---|---|
| 문제 | `gap`의 대상과 문제 | `problem` |
| 방법 | `approach`의 Core claim, Mechanism, Procedure | `method` |
| 가정 | `approach`의 Assumptions | `assumptions` |
| 평가 | `evaluation`의 Comparisons, Measurement | `evaluation` |

Solar 출력 형식:

```json
{ "problem":     { "match": "same | partial | different", "reason": "...", "quote": "카드에서 가져온 문장" },
  "method":      { ... }, "assumptions": { ... }, "evaluation": { ... } }
```

- `same`, `partial`, `different`의 뜻은 [J-3](#j-3-요소-일치)에 있습니다. 카드 필드가 비어 있으면(대조 실패 포함) 그 요소는 `different`가 아니라 **`unknown`**으로 둡니다. "논문에 없음"과 "확인 못 함"을 섞지 않기 위해서입니다.
- V5의 최근접 순서는 [J-4](#j-4-최근접-순서)를 따릅니다.

### 4.4 판정 (V8, 코드)

판정 규칙은 [J-5](#j-5-판정)에 있습니다. 화면에서는 판정마다 이렇게 안내합니다.

| 판정 | 화면 |
|---|---|
| `solved` | 그 논문과 겹치는 요소를 보여 주고, 다른 후보 검증 또는 수정을 권함 |
| `partial` | 겹치는 요소와 다른 요소를 나눠 보여 줌 |
| `not_addressed` | 가장 가까운 논문과의 차이를 보여 줌 |

판정 메시지에는 "이 주제로 확정"과 "다른 후보 검증" 버튼이 붙고, 수정은 입력창으로 요청합니다 (이슈 #15). 워크플로우의 자동 수정 루프는 시간 관계상 넣지 않습니다.

### 4.5 비평 (V9)

loop2의 `review.md` 필드와 ScholarIdeas 7요건을 합칩니다. 참고문헌으로는 최근접 3편의 카드만 넘깁니다.

```json
{
  "requirements": {
    "problem_scope":      { "status": "defined | undecided | not_applicable", "note": "..." },
    "difference":         { ... },
    "mechanism":          { ... },
    "method_definition":  { ... },
    "validation_design":  { ... },
    "alternative_explanations": { ... },
    "failure_feasibility": { ... }
  },
  "unsupported": "근거 없는 주장",
  "vague": "검증을 막는 빈 정의나 절차",
  "already_done": "이미 한 부분과 그 논문 ID",
  "suggestion": "가장 중요한 설계 개선이나 최소 판별 실험"
}
```

| 7요건 키 | 뜻 |
|---|---|
| `problem_scope` | 문제와 범위 |
| `difference` | 기존 연구와의 차이 |
| `mechanism` | 핵심 메커니즘 |
| `method_definition` | 방법 정의 |
| `validation_design` | 검증 설계 |
| `alternative_explanations` | 대안 설명 배제 |
| `failure_feasibility` | 실패 조건과 실행 가능성 |

`defined`는 "명시되어 있다"는 뜻일 뿐 타당하다는 보장이 아닙니다. 화면에도 그렇게 적습니다. 7요건은 AI 5개 사례로 만든 잠정 기준 v0라는 한계도 함께 표시합니다.

### 4.6 Studio 에이전트 B 설정

Studio 콘솔에서 **직접 만드셔야 하는 부분**입니다.

| 단계 | 종류 | 설정 |
|---|---|---|
| 1 | 문서 파싱 (OCR) | PDF 전체. 쪽 번호 유지 |
| 2 | 정보 추출 | 아래 스키마. 지침: "각 필드에 논문 본문의 문장을 `quote`로 그대로 복사하고 쪽 번호를 적는다. 해당 내용이 없으면 빈 문자열로 둔다. 결과 수치는 넣지 않는다." |

추출 스키마는 4.2의 카드에서 `paper_id`, `level`을 뺀 것입니다. 이 두 값은 코드가 채웁니다.

호출할 때는 `include=["all"]`로 1단계 파싱 결과도 함께 받습니다. 인용 대조(4.2)에 쓰기 위해서입니다. 에이전트 ID는 `.env`의 `STUDIO_CARD_AGENT_ID`에 둡니다. 에이전트 A는 `STUDIO_OP_AGENT_ID`입니다.

## 5. 최종 주제 카드 (⑤, 코드만)

LLM을 부르지 않고 저장된 값으로만 조립합니다. 워크플로우 4.5 형식을 따릅니다.

| 항목 | 가져오는 곳 |
|---|---|
| 주제 | ③ 후보의 `title`, `summary` |
| 출발 문제 | ① 추천 카드의 `title`과 출처 논문 |
| 연구 설계 | ③ 후보의 `gap`, `approach`, `evaluation` |
| 가장 가까운 연구 | ④ 최근접 3편과 요소별 일치 여부, 인용 |
| 판정 | ④ 판정과 읽은 수준 |
| 빈틈 | 최근접 논문의 `limitations` 인용 |
| 비평 | ④ 7요건 상태표, `suggestion` |
| 조사 범위 | 검색어, 검색한 논문 수, 본문까지 읽은 논문 수, 조사 날짜 |

마크다운 내보내기(R-2)는 브라우저에서 이 카드를 문자열로 바꿔 내려받게 합니다.

## 6. 저장

**결정 (2026-11-05): 두 단계로 갑니다.**

| 단계 | 저장 위치 | 이유 |
|---|---|---|
| 지금 | 로컬 폴더 `DB/` (`config.DB_DIR`) | 외부 설정 없이 바로 구현 가능 |
| `feature/supabase` 브랜치 | **Supabase** (무료 플랜) 테이블 | Render의 디스크는 재배포·재시작 때 지워짐. 로그인 데이터, 작업 결과, Studio 카드 캐시가 유지되어야 함 |

코드는 처음부터 `src/store.py` 같은 저장 계층 뒤에서만 파일을 읽고 쓰게 하고, Supabase 단계에서 그 구현만 바꿉니다. 아래 6.1, 6.2는 지금 단계의 경로이고, 6.3이 Supabase 단계의 테이블입니다.

### 6.1 작업 결과와 캐시

| 경로 | 내용 | 보관 |
|---|---|---|
| `DB/runs/{run_id}.json` | ①·③·④ 결과. 지금 `DB/sessions/`를 이름만 바꿈. `owner_session` 필드로 어느 세션 것인지 기록 | 비로그인 24시간, 로그인은 세션과 함께 |
| `DB/abstract_cards/{paper_id}.json` | V4 초록 카드 | 계속 |
| `data/papers/pdf/{paper_id}.pdf` | ④에서 받은 PDF | 계속 |
| `data/papers/studio/{paper_id}.card.json` | Studio B 결과 (카드 + 파싱 원문) | 계속. **같은 논문은 다시 읽지 않음** |

### 6.2 사용자 데이터

| 경로 | 내용 | 요구 |
|---|---|---|
| `DB/users/{user_id}/user.json` | `google_sub`, `email`, `name`, `created_at` | A-1 |
| `DB/users/{user_id}/profile.json` | 프로필 | P-3 |
| `DB/users/{user_id}/sessions/{session_id}.json` | 세션 전체 (API 명세 2.2 형식) | S-1, S-2 |
| `DB/feedback.jsonl` | 한 줄에 피드백 하나 | O-3 |
| `DB/logs/calls-YYYYMMDD.jsonl` | 한 줄에 호출 하나 | O-1 |

- `user_id`는 Google의 `sub` 값을 해시한 문자열입니다. 이메일을 폴더 이름에 쓰지 않기 위해서입니다.
- 세션 목록(`GET /api/sessions`)은 그 사용자의 `sessions/` 폴더를 읽어 만듭니다. 사용자당 세션 수십 개면 충분히 빠릅니다.
- **쓰기는 임시 파일에 쓴 뒤 이름을 바꿉니다.** 쓰는 도중에 서버가 죽어도 파일이 반쯤 깨지지 않습니다. `version_conflict` 검사와 쓰기는 사용자별 잠금 안에서 합니다.
- 호출 로그 한 줄에는 `ts`, `session_id`, `run_id`, `step`, `provider`(`solar` · `studio` · `s2`), `model`, `prompt_name`, `prompt_hash`, `input`, `output`, `latency_ms`, `tokens_in`, `tokens_out`, `status`(`ok` · `error` · `cancelled`)가 들어갑니다.
- `DB/users/`, `DB/runs/`, `DB/logs/`, `DB/feedback.jsonl`, `DB/abstract_cards/`는 `.gitignore`에 추가합니다.

### 6.3 Supabase 단계

| 테이블 | 열 | 대체하는 것 |
|---|---|---|
| `profiles` | `user_id` (Supabase Auth 사용자 ID), `json`, `updated_at` | `DB/users/*/profile.json` |
| `sessions` | `id`, `user_id`, `title`, `stage`, `json`, `updated_at` | `DB/users/*/sessions/` |
| `runs` | `id`, `owner_session`, `user_id` (비로그인은 null), `json`, `created_at` | `DB/runs/` |
| `cache` | `kind` (`abstract_card` · `studio_card`), `key` (S2 `paper_id`), `json`, `created_at` | `DB/abstract_cards/`, `data/papers/studio/` (로컬 파일은 사본으로 남김) |
| `feedback` | `id`, `session_id`, `target`, `target_id`, `value`, `comment`, `created_at` | `DB/feedback.jsonl` |
| `call_log` | 6.2의 호출 로그 필드 | `DB/logs/` |

- 사용자 테이블은 따로 만들지 않습니다. Supabase Auth가 사용자를 관리합니다.
- 서버만 `service_role` 키로 테이블에 접근합니다. 브라우저는 로그인에만 Supabase를 쓰고, 데이터는 항상 우리 API를 거칩니다. 그래서 행 단위 보안(RLS)은 모든 테이블에서 켜 두고 공개 정책은 만들지 않습니다.
- PDF 파일은 저장하지 않습니다. Studio 카드가 캐시되면 PDF를 다시 받을 일이 없습니다.
- 테이블을 만드는 SQL은 [`docs/supabase.sql`](supabase.sql)입니다. Supabase 대시보드의 SQL 편집기에 붙여 넣어 실행합니다.
- **`feature/supabase`에서 옮긴 것:** 로그인(`src/auth.py`), `profiles`·`sessions`·`runs`(`src/store.py`). `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`가 없으면 6.2의 `DB/users/` 폴더에 저장합니다. 비로그인 결과는 그대로 `DB/runs/`에 24시간 둡니다. `feedback`, `call_log`는 아직 로컬 파일입니다.
- **`cache`(#34):** `src/paper_cache.py`. 로컬 파일 → `cache` 테이블 순서로 읽고, 새로 만든 카드는 둘 다에 씁니다. Supabase 호출이 실패하면 캐시 없이 진행합니다. S2 검색 응답은 캐시하지 않습니다. 검색어를 Solar가 매번 새로 써서 같은 검색어가 거의 다시 나오지 않기 때문입니다.
- 무료 플랜은 오래 쓰지 않으면 프로젝트가 일시 정지됩니다. 시연 전에 대시보드에서 상태를 확인합니다.

## 10. 판단 기준

[topic_recommendation_workflow.md](topic_recommendation_workflow.md)의 **흐름은 그대로 두고**, 그 문서 5장의 기준 C1~C13은 이 장으로 대체합니다. C1~C13의 수치는 근거 없이 정한 값이었습니다.

### 10.1 원칙

모든 기준에 **근거 종류**를 붙입니다. 근거가 없는 수치는 숨기지 않고 `시작값`으로 표시하고, 언제 무엇으로 고칠지 함께 적습니다.

| 근거 종류 | 뜻 | 바꿀 때 |
|---|---|---|
| **정의** | 수치가 없는 규칙. 서비스가 지켜야 할 성질 자체 | 요구사항이 바뀔 때만 |
| **차용** | evaluation_v2, loop2에서 이미 쓰고 결과를 확인한 형식이나 규칙 | 원래 실험의 결론이 바뀔 때 |
| **유도** | 다른 값에서 계산한 수치 | 원래 값이 바뀌면 다시 계산 |
| **시작값** | 근거 없이 정한 수치 | 적힌 측정을 한 뒤 |

판정에는 가능하면 **점수 합계 대신 요소의 조합**을 씁니다. "3점 이상" 같은 문턱값은 근거를 대기 어렵지만, "문제와 방법이 같다"는 뜻을 설명할 수 있기 때문입니다.

**③ 참고문헌을 고르고 넘기는 방법**

1. 초록 없는 논문과 중복을 뺀다.
2. Solar가 제목과 초록만 보고, 고른 문제와 관련 없는 S2 결과를 한 번의 호출로 뺀다. 핵심만 남길 만큼 좁히지는 않는다. evaluation_v2에서 핵심 문헌만 준 조건(B)이 전체를 준 조건(A)보다 낫지 않았기 때문이다.
3. 검색어별로 번갈아 뽑아 25편을 채운다. 첫 검색어의 결과가 대부분을 차지하지 않게 하기 위해서다. 모자라면 있는 만큼만 넘긴다.
4. 형태는 제목, 연도, 초록, 찾은 검색어. 카드로 요약하지 않는다 (조건 C가 나아지지 않음).
5. 제안과 수정 호출에는 25편 전부를 넣는다. 상호 검토와 토너먼트 판정에는 **해당 후보가 인용한 논문만** 넣는다. ③의 토큰 대부분이 여기서 나오므로, 이 규칙이 시간을 가장 크게 줄인다 (계산상 13분 → 약 4분, 실측 전).

**확인:** persona 시나리오에서 V3을 30편으로 한 번 돌려, 15편일 때와 최근접 3편이 같은지 본다. 같으면 15편을 유지하고, 다르면 늘린다.

# 연구 주제 추천 워크플로우

사용자 프로필에서 출발해, 기존 연구와 겹치지 않는 연구 주제에 도달하기까지의 흐름을 정리한 설계안입니다.

- **상태:** 구현 전 설계안
- **근거:** 2109.13916의 `5.1 ML for Cybersecurity`로 진행한 수동 PoC (2026-10-31)
- **범위 (2026-11-05):** ② 문제 파고들기는 대화형으로 구현합니다. 2.2~2.7의 세부 흐름 묶기는 이번 범위 밖입니다.
- **기준 대체 (2026-11-05):** 이 문서는 흐름만 유효합니다. 5장 C1~C13과 본문의 수치는 [설계서.md](설계서.md) 10장의 J-1~J-8로 대체했습니다.
- **주의:** 숫자와 기준은 모두 시작값이며 아직 검증하지 않았습니다. PoC에서 LLM 역할은 Solar가 아니라 Claude가 수동으로 맡았으므로, Solar의 품질과 응답 시간은 측정되지 않았습니다.

## 1. 대화 상태

대화는 하나의 줄기로 위에서 아래로 이어지고, 상태는 지금 위치를 나타냅니다. 앞 상태로 되돌아가는 조작은 없습니다 (이슈 #15). 방향을 바꿀 때는 아래 "방향을 바꾸는 경로"처럼 새 메시지를 이어 붙이고, 처음부터 다시 하려면 새 대화를 엽니다.

| 상태 | 사용자가 보는 것 | 사용자가 하는 일 | 나가는 조건 |
|---|---|---|---|
| **① 둘러보기** | 추천 리스트와 추천 이유 | 질문, 비교, 거절, 조건 추가 | 문제 1개 선택 |
| **② 문제 파고들기** | 세부 흐름 3~5개와 요약 | 질문, 세부 흐름 선택 | 세부 흐름 1개 선택 |
| **③ 주제 다듬기** | 판정이 붙은 후보 3개 | 후보 선택, 연구 설계 구체화 | 구체화 완료 |
| **④ 검증** | 진행 상태, 재판정, 본문 인용 | 판정 수용 또는 수정 요청 | 사용자가 판정을 수용 |
| **⑤ 확정** | 최종 주제 카드 | 저장 | 종료 |

## 2. 단계 표시

| 표시 | 뜻 | 신뢰 수준 |
|---|---|---|
| **[코드]** | 같은 입력이면 같은 결과 | 높음 |
| **[API]** | S2, Upstage 호출 (실패와 재시도 처리 필요) | 외부 품질에 좌우 |
| **[LLM-제한]** | 기준과 출력 형식을 고정하고 결과를 검사할 수 있음 | 평가 후 사용 |
| **[LLM-의존]** | 생성이나 추론이 중심이라 기준만으로 품질을 보장하기 어려움 | **보완 필요** |
| **[사용자]** | 사용자의 선택이나 입력 | 해당 없음 |

## 3. 세부 흐름도

`C1`~`C13`은 [5장의 자체 기준](#5-자체-기준)을 가리킵니다.

```text
[폼 입력] 분야, 관심사, 보유 자원, 제약
   │
═══ ① 둘러보기 ═══════════════════════════════════════
   │
   ├─ 1.1 [API]      프로필을 쿼리로 임베딩
   ├─ 1.2 [코드]     all.json과 코사인 검색 → 기준 C1로 필터
   ├─ 1.3 [LLM-제한] 문제별 추천 이유 작성 (프로필 항목과 연결)
   ├─ 1.4 [사용자]   질문, 비교, 거절, 조건 추가 → 문제 1개 선택
   │      └ 자기 아이디어 제시 → 3.3으로 직행
   │
═══ ② 문제 파고들기 ═══════════════════════════════════
   │
   ├─ 2.1 [LLM-의존] 문제와 프로필 → 검색어 3~5개 (C2)
   ├─ 2.2 [API·코드] S2 검색 + 인용논문 합치기, 중복 제거 (C3)
   ├─ 2.3 [LLM-제한] 제목·초록으로 관련성 선별 (C4)
   ├─ 2.4 [LLM-제한] 초록을 구조화 필드로 변환 (C5)
   ├─ 2.5 [코드]     type·target 기준으로 세부 흐름 묶기 (C6)
   ├─ 2.6 [LLM-제한] 흐름 이름과 요약 작성 (소속 논문 내용만 사용)
   ├─ 2.7 [사용자]   세부 흐름 1개 선택
   │
═══ ③ 주제 다듬기 ═════════════════════════════════════
   │
   ├─ 3.1 [API·코드] 근거 카드 수집: 초록 + 한계 스니펫 (C7)
   ├─ 3.2 [LLM-의존] 근거 카드 + 문제 + 프로필 → 후보 3개
   │      └ [코드] 유효성 검사 통과분만 유지 (C8)
   ├─ 3.3 [LLM-제한] 후보를 대상·문제·방법·평가로 분해 (C9)
   ├─ 3.4 [LLM-의존] 요소 조합으로 검증 검색어 3개 생성
   ├─ 3.5 [API]      논문 + 스니펫 검색
   ├─ 3.6 [API·코드] 임베딩으로 15편까지 축소
   ├─ 3.7 [LLM-제한] 요소별 비교: 일치·부분·불일치 + 인용 (C10)
   ├─ 3.8 [코드]     점수 합산 → 최근접 2~3편, 판정 (C11)
   │      │
   │      ├ 전부 solved → 3.9 [LLM-의존] 후보 수정 → 3.3으로 (C12)
   │      └ 그 외 ↓
   ├─ 3.10 [사용자]  판정이 붙은 후보 1개 선택
   ├─ 3.11 [LLM-의존] 질문으로 연구 설계 구체화 (C13)
   │      └ 문제·방법 변경 시 3.3으로, 세부 조건만 변경 시 진행
   │
═══ ④ 검증 (백그라운드) ═══════════════════════════════
   │
   ├─ 4.1 [API]      최근접 논문 PDF 수집, Document Parse
   ├─ 4.2 [코드·API] 요소별로 관련 문단 검색
   ├─ 4.3 [LLM-제한] 본문 기준으로 요소 재비교 (C10)
   ├─ 4.4 [코드]     재판정 (C11)
   │      ├ solved → 3.9로 (C12 예산 내)
   │      ├ 전제 틀림 → 4.5 [LLM-의존] 범위 조정 → 3.3으로 1회
   │      └ 유지 ↓
   ├─ 4.6 [사용자]   판정 수용 또는 수정 요청
   │
═══ ⑤ 확정 ═══════════════════════════════════════════
   │
   └─ 5.1 [코드]     저장된 값으로 최종 주제 카드 조립
```

### 방향을 바꾸는 경로

앞 단계의 결과는 `run_id`로 저장해 재사용합니다. 처음부터 다시 돌리면 S2 호출을 낭비합니다. 화면은 앞 상태로 돌아가지 않고, 같은 대화 아래에 새 메시지를 붙입니다.

| 지금 상태 | 사건 | 대화에 붙는 것 | 재사용하는 것 |
|---|---|---|---|
| ① | 추천이 다 마음에 안 듦 | 제외 이유를 남기고 "다시 추천 받기" → 새 추천 메시지 | 거절 이유 |
| ③ | 조건이 바뀜 | 대화로 조건을 말하고 "후보 다시 만들기" → 새 후보 메시지 | 프로필, 대화 |
| ④ | 판정이 `solved`이거나 다른 후보를 보고 싶음 | "다른 후보 검증" → 후보 카드를 다시 보인 메시지 (상태 ③) | 후보 생성 결과 |
| ④ | 판정을 받아들이지 않음 | 입력창으로 수정 요청 | 판정 결과 |
| 어디서든 | 방향을 크게 바꿈 | 새 대화 | 계정 프로필 |

## 4. 주요 판단 방법

### 4.1 최근접 논문 판별

S2는 후보 주제와의 최근접 논문을 알려 주지 않습니다. 검색 순위는 검색어 관련도이고, 추천 API의 입력은 논문 ID입니다. 따라서 S2로 논문을 모으고, 판별은 직접 합니다.

**기준은 후보의 핵심 요소를 얼마나 이미 다뤘는가입니다.** 인용 수는 영향력일 뿐 겹침이 아니므로 쓰지 않습니다.

1. 후보를 대상·문제·방법·평가로 분해합니다.
2. 검색 결과를 임베딩 유사도로 15편까지 줄입니다. 비용을 줄이는 필터일 뿐 최근접을 결정하지 않습니다.
3. Solar가 요소별로 비교하고 원문 인용을 붙입니다.
4. 점수 합 상위 2~3편을 최근접으로 정합니다. 동점이면 최신 논문을 앞에 둡니다.

**PoC 후보 "적대적 패치 루프의 기능 손실" 적용 예** (수동으로 매긴 값)

| 논문 | 대상 | 문제 | 방법 | 평가 | 합계 |
|---|---|---|---|---|---|
| P2Patch | 일치 2 | 부분 1 | 부분 1 | 불일치 0 | **4** |
| Fixing, Breaking, or Faking It? | 부분 1 | 일치 2 | 불일치 0 | 부분 1 | **4** |

### 4.2 구조화 출력 예

```json
{
  "paper": "VulnRepairEval",
  "type": "평가·벤치마크",
  "target": "LLM의 취약점 패치",
  "domain": "Python CVE 23건",
  "method": "컨테이너 기반 PoC 차등 검증",
  "evaluation": "원본 익스플로잇 실행 실패 여부",
  "assumption": null,
  "limits": ["부정확한 취약점 식별", "패치의 문법·의미 오류"],
  "quotes": ["각 필드의 근거 문장"]
}
```

### 4.3 세부 흐름 묶기 예

PoC의 패치 검색 결과 12편에 적용한 결과입니다. 제목 기준이라 일부 분류는 추정입니다.

| 세부 흐름 | 논문 |
|---|---|
| **평가 방법론** | Metrics Failure, VulnRepairEval, Semantic-Aware Normalization, Statistical Implausibility Detection |
| **패치 생성 방법** | LLM4CVE, APPATCH, Enhanced AVR, SECUREPATCH, RAG 기반 수리 |
| **기타 (3편 미만)** | Adversarial Bug Reports |
| **기타 (도메인 특화)** | LogicRepair, Obfuscated Smart Contracts |

### 4.4 근거 카드 형식

원문 인용과 LLM 추론을 분리합니다. LLM 판정을 다시 근거로 쓰지 않기 위해서입니다.

```text
논문: PatchBench (arXiv 2609.04075)
종류: 초록 | 스니펫 | 본문
원문 인용: (textnorm.contains로 검증한 문장)
내용: PoC만으로 검증하면 해결률이 평균 1.83배 부풀려짐
이 논문이 다루지 않은 것: (LLM 추론, 근거로 쓰지 않음)
```

### 4.5 최종 주제 카드 형식

| 항목 | PoC 후보의 예 |
|---|---|
| **주제** | 적대적 패치 루프에서 기능 평가를 분리한 라운드별 측정 |
| **출발 문제** | ML for Automated Security Patching |
| **가장 가까운 연구** | P2Patch, Fixing, Breaking, or Faking It? |
| **판정** | `partial` + 원문 인용 |
| **빈틈** | 보안 평가는 분리됐지만 별도 기능 평가는 찾지 못함 |
| **남은 위험** | 효과가 작을 가능성, 기능 평가 세트 구축의 어려움 |
| **조사 범위** | 확인한 논문 수와 읽은 수준, 조사 날짜 |

## 5. 자체 기준

> **대체됨.** 아래 기준은 근거 없이 정한 값이라 [설계서.md 10장](설계서.md#10-판단-기준)으로 대체했습니다. 기록용으로만 남깁니다.

| ID | 단계 | 대상 | 기준 |
|---|---|---|---|
| **C1** | 1.2 | 추천 필터 | 검증 통과 항목만 사용. 논문당 최대 2개. `MIN_SCORE`는 현재 0.40으로 무관한 주제도 통과하므로 재조정 필요 |
| **C2** | 2.1 | 검색어 | 3~6단어 키워드형. 문장 금지. 최소 1개는 문제 원문 키워드 사용 |
| **C3** | 2.2 | 수집 | 최근 3년 우선. 검색어당 20편, 합계 50편 이하. 0건이면 단어를 줄여 1회 재시도 |
| **C4** | 2.3 | 관련성 | 문제 자체를 다루면 통과. 같은 도메인의 다른 문제, 배경 언급은 제외. 초록 없으면 제외하고 건수 기록 |
| **C5** | 2.4 | 구조화 | 초록에 없으면 `null`. `type`은 고정 라벨 6개 중 선택 (`새 방법 제안`, `평가·벤치마크`, `공격·위험 분석`, `실증 연구`, `서베이`, `입장 논문`). 값마다 근거 문장 필수 |
| **C6** | 2.5 | 묶기 | 1차 `type`. 3편 이상이면 흐름, 미만이면 기타. 10편 초과면 `target`으로 분할. 서베이는 참고 자료로 분리. 최대 5개 |
| **C7** | 3.1 | 근거 카드 | 흐름당 최대 10장. 원문 인용은 `textnorm.contains` 통과 필수. 출처 종류(초록·스니펫·본문) 기록 |
| **C8** | 3.2 | 후보 유효성 | 근거 카드 1장 이상 인용. 네 요소를 모두 채움. 근거 없는 후보는 폐기 |
| **C9** | 3.3 | 요소 분해 | 각 요소는 한 문장. 후보 문장에 없는 내용을 더하면 안 됨 |
| **C10** | 3.7, 4.3 | 요소 비교 | 일치 2, 부분 1, 불일치·언급 없음 0. 인용이 없거나 검증 실패면 0 |
| **C11** | 3.8, 4.4 | 판정 | 한 논문이 네 요소 모두 일치면 `solved`. 합계 3점 이상이면 `partial`. 그 외 `not_addressed`. 초록 기준 결과에는 "초록 수준" 표시 |
| **C12** | 3.9, 4.4 | 수정 루프와 예산 | 수정 최대 2회. 요청당 S2 호출 60회, PDF 후보당 2편. 초과 시 "찾지 못함"과 조사 범위 보고 |
| **C13** | 3.11 | 구체화 완료 | 데이터, 방법, 평가 지표, 비교 기준, 필요 자원의 5개 항목이 채워지고 사용자가 확인 |

여러 논문을 합쳐 네 요소가 다 채워져도 `solved`가 아닙니다. 그 조합은 아직 아무도 안 했을 수 있기 때문입니다. 반대로 초록에 없는 내용은 0점이 되므로, 초록 기준의 `not_addressed`는 신뢰도가 낮습니다.

## 6. LLM 의존 지점과 보완 방법

### 위험 높음: 품질을 기준으로 보장하기 어려움

| 단계 | 추상적인 지점 | 실패 모습 | 보완 방법 |
|---|---|---|---|
| **3.2 후보 생성** | "좋은 연구 주제"의 정의가 없음 | 근거만 붙인 뻔한 주제, 실행 불가능한 주제 | 생성 전략 고정 (예: 최근접 논문이 세운 기준을 다른 축에 적용, 두 논문의 한계 결합). 사람 평가 루브릭 작성 |
| **3.9 후보 수정** | "빈틈"을 찾는 추론 | 사소한 차이만 바꿔 새 주제처럼 보이게 함 | 어느 요소가 바뀌었는지 명시 강제. 대상이나 도메인만 교체한 후보는 금지 또는 경고 |
| **3.11 구체화** | 대화의 깊이와 조언의 타당성 | 실현 불가능한 설계에 동의 | C13 항목 채우기로 제한. 제약과 충돌하면 경고. 논문 언급은 Tool 결과로 제한 |
| **4.5 범위 조정** | 어디까지 좁힐지 판단 | 너무 좁아져 의미 없는 주제가 됨 | 본문 인용으로 빠진 요소만 남김. 사용자 확인 필수 |

## 7. 구현 전 확인할 것

1. **3.7 요소 비교:** 판정 전체가 여기에 달려 있으므로, PoC 후보와 가까운 논문 쌍을 사람이 라벨링해 Solar 판정과의 일치율부터 측정합니다.
2. **3.2 후보 생성:** 고정 전략을 쓴 후보가 자유 생성보다 나은지 사람이 평가합니다.
3. **2.1, 3.4 검색어:** 0건이나 노이즈가 얼마나 나오는지 확인합니다. PoC에서 문제가 실제로 드러난 부분입니다.

## 8. 기존 설계와의 차이와 남은 결정

**기존 설계(`LLMOps_Paper_subject_searching_Agnet/CLAUDE.md`)와 달라지는 점**

- **검증이 두 단계로 나뉩니다.** 기존 설계는 사용자가 고른 주제만 검증하도록 권장합니다. 이 흐름은 고르기 전에 초록 수준 검증을 돌립니다. PoC에서 초기 후보 3개가 모두 탈락했기 때문입니다. 대신 S2 호출과 응답 시간이 늘어납니다.
- **사용자 선택이 하나 늘어납니다.** 세부 흐름 선택(2.7)이 추가됩니다.
- **계보를 미리 만들지 않습니다.** 2.2~2.6을 요청 시점에 돌리고, 자주 찾는 문제의 결과를 저장해 재사용합니다. 이 저장 결과가 곧 러프한 계보입니다.

**남은 문제**

- **대기 시간:** 2.1~2.6과 3.1~3.8에 호출이 몰립니다. 시간은 아직 재지 않았습니다. 처음 찾는 문제는 진행 상태를 보여 줘야 합니다.
- **검증 중 주제 변경:** ④가 백그라운드로 도는 동안 주제가 바뀔 수 있으므로, 시작 시점의 주제를 저장하고 어느 버전의 판정인지 표시해야 합니다.
- **선행 구현:** Document Parse 호출 코드가 아직 없어 4.1은 그 구현이 먼저 필요합니다.
- **입력 품질 전파:** 2.5, 3.8처럼 코드로 처리되는 단계도 입력인 LLM 필드의 품질에 영향을 받습니다.
